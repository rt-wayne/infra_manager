# 第 125 項：登入端點限次（防止替同事連錯密碼讓 WPX 鎖住公司帳號）

## 目標

登入端點 `POST /auth/login` 不必登入即可呼叫，背後把工號＋密碼轉給 WPX 驗證；WPX 對同一工號連錯會鎖住該員工的**公司帳號**（全公司系統都登不進去）。本系統要在轉給 WPX 之前自己限次，讓任何人都無法透過本系統把同事的公司帳號鎖住。一起做第 128 項 X1（工號字元白名單，防 log 偽造）與 X2（密碼長度上限，防加密超限被歸為服務異常）。

## 分析摘要（architect 2026-10-22；裁示前的分析，動工時參考）

1. **鍵**：殼 jar 轉給後端只帶 `Authorization`、`Content-Type`（`infra_manager_web\...\BackendForwarder.java:128-138`），無 `X-Forwarded-For`；UAT 路徑為瀏覽器 → 殼 jar → Apache → 後端（`SETUP.md:404-410`），後端看到的來源全公司一樣，依 IP 限次等於全域限次。要做 IP 須殼 jar 以 `getRemoteAddr` 覆寫自訂 header、後端只在來源是 Apache／殼 jar 時信任，與 PRD 偏離表第 18 列（稽核不記 IP，使用者 2026-10-19 裁示維持）同一件事。每個工號的計次低於 WPX 門檻時，噴灑多工號也鎖不住人，IP 的邊際價值主要是事後追查。
2. **門檻**：`VerifySecure-Client.md:197` 只寫「-3 永久鎖定、-4 已鎖定、-5 鎖定中」，沒有連錯次數、鎖定時長、計數何時歸零。本系統上限最好是「WPX 門檻減 2」（WPX 計數推定全公司共用，本人在別系統打錯也累加），最低 2。若 WPX 計數只在成功時歸零、不隨時間衰減，固定窗口擋不住有耐心的攻擊者，冷卻期要拉長到 WPX 衰減期以上。比照 `WpxAuthClient.java:157` 以 `@Value("${…:3}")` 帶預設值，WPX 回覆後在 `environment.properties` 加一行覆寫。
3. **計次範圍**：-1 要計，否則送幾次就能從「有沒有出現限次訊息」分辨工號是否存在（現行 -1 與密碼錯同回 A01，`WpxAuthClient.java:217`）；-2～-10 要計（對已鎖帳號持續送可能延長或升級成永久鎖定）；A05 不計（WPX 一掛全員被擋）；X1／X2 被擋不計（否則超長密碼就能不經 WPX 擋人）；成功與 A04 歸零。**並發繞過**：「先查 → 呼叫 → 再記」會讓同時送的 50 筆全部打到 WPX；改「預扣」——`ConcurrentHashMap.compute` 原子檢查並加一，成功刪除、服務異常退回、失敗保留。
4. **狀態**：PRD 已以「同時只有一個後端」為前提（`PRD.md:375`、`:383`、`:407`）；pom 無 Caffeine／Bucket4j／Resilience4j。記憶體：重啟清空（攻擊者多一輪，重啟也是解除被擋的維運手段）；DB：要 DDL、每筆失敗寫 DB、MERGE 處理並發，只有多實例才值得；殼 jar：要解析帳密本文，破壞「殼 jar 不解析帳密」設計（`infra_manager_web\...\AuthController.java:8`）。清理：寫入超過軟上限掃過期，仍超過硬上限（例 10 萬筆）時對新工號直接擋、每分鐘最多一行 WARN（放行會讓「先灌滿再攻擊」繞過）。記憶體估算：白名單＋併發上限把灌入壓在約每秒百筆，15 分鐘約 9 萬筆、每筆百餘 byte，約十數 MB。
5. **回應**：前端顯示後端 `message` 不看狀態碼（`src\api\errors.ts:10-14`），401 導回已排除 `/auth/login`（`src\api\http.ts:30-31`、`:79`），殼 jar 非 2xx 原樣回傳（`BackendForwarder.java:146-150`），前端與殼 jar 不必改。不用 5xx：`GlobalExceptionHandler.java:49-50` 每筆 5xx 都 `log.error` 加完整堆疊。`ApiException`（`com.mpx.infra_manager.common`，可改）補 429 工廠。「擋本系統」比「鎖公司帳號」輕：只影響本系統、冷卻到期或重啟即解除、不會升級永久；代價是攻擊者每個冷卻期送 3 次就能讓受害者在本系統一直登不進去，被擋期間正確密碼也進不去，且查不到是誰。
6. **併發上限**：一次登入最多呼叫 WPX 四次（公鑰快取過期 GET＋POST，收到 -23 換鑰再 GET＋POST，`WpxAuthClient.java:186-190`、`:229`、`:265-268`），連線與讀取逾時各 10 秒（`:159-162`），最壞約 80 秒；取公鑰 `synchronized`（`:262`），WPX 卡住時登入排在同一把鎖後面；Tomcat 預設 200 執行緒與其他 API 共用，約 200 個卡住的登入讓整個系統停擺；殼 jar 讀取逾時 120 秒（`BackendForwarder.java:68`）。做法：JDK `Semaphore` 同時最多 N（建議 10，帶預設值設定）個，拿不到立即回 429、不排隊；計次放在併發上限之前，拿不到名額時退回預扣。約 20 行、不加套件。
7. **判斷順序**：① 工號空白或不符白名單（X1）、密碼空白或超過字元上限（X2 第一層）→ A01，不送 WPX、不計次 → ② 同一工號已達上限 → A06／429 → ③ 併發上限已滿 → A07／429、退回預扣 → ④ WPX 驗證；加密前內層位元組超過公鑰上限（X2 第二層）→ A01、不呼叫 WPX、退回預扣 → ⑤ 依結果記次。X1 在計次之前，Map 的鍵與限次 log 才不含換行。
8. **X2 計算**：內層 JSON 除密碼外固定開銷 83 bytes＋工號 7 碼＝90 bytes；RSA-OAEP（SHA-1）上限＝公鑰位元組 − 42：2048 位元 214 bytes（`VerifySecure-Client.md:158`）留給密碼 124 bytes（ASCII 約 124 字、中文約 41 字），4096 位元 470 bytes 留 380 bytes。Jackson 把控制字元跳脫成 6 byte 的 `\u00XX`，128 字元最壞可達 768 bytes，所以第二層在 `WpxAuthClient.java:234` 加密前用快取公鑰的 modulus 位元數算實際上限。交付文件測試環境公鑰範例 `keySize: 2048`（`VerifySecure-Client.md:100`），正式未知。
9. **log**：工號剛進入暫停時記一行 WARN（例「登入暫停 userId=… 15 分鐘內失敗 3 次，暫停至 HH:mm」）；暫停期間被擋的請求不逐筆記，每分鐘最多一行彙總（在下一筆請求時順帶輸出，不另開排程；最後一批要等下一筆請求才寫出）；併發上限滿、Map 滿同樣每分鐘最多一行。殼 jar 每筆非 2xx 一行 WARN 是既有行為，本項不改。log 無總容量上限另登記第 129 項。
10. **測試**：新元件（暫名 `LoginThrottle`，建構子注入 `Clock`）用可前進的假時鐘測：第 3 次失敗後第 4 次被擋且不呼叫 WPX、窗口到期放行、成功歸零、服務異常退回預扣、A04 歸零、大小寫同鍵、硬上限新工號被擋舊工號不受影響、每分鐘一行彙總（Logback `ListAppender`）、`CountDownLatch` 同放 20 執行緒斷言 WPX mock 呼叫 ≤ 上限、WPX mock 阻塞時第 N+1 筆立即 A07。`AuthServiceTest` 建構多一參數並補 X1 案例（`\r\n`、全形字、31 字）；`WpxAuthClientTest` 補 2048 位元下內層超長回 A01 且未送 POST。

## 查證結果

### 工號格式（2026-10-22 測試 DB `itflow_uat` 唯讀查詢，`UserIdFormatProbe`，不印工號本身）

- `IM_ACCT_USER` 13 筆全部是 7 碼純數字。
- 同步表 `PX_SYNC_EMP`（STATUS＝1）53,810 筆：非「純數字 1～7 碼」9,030 筆、非「英數 1～30 字」1,366 筆；長度 2～18 碼。非純數字者樣態以「英文 1 碼＋數字 5～6 碼」最多（7,349 筆），其次是「英文＿英文」帳號式（含底線）數百筆，另有少量含 `-`、`*`、`+`。
- 有資訊部部門列者（任一部門，近似資格口徑）113 人，**全部是純數字 1～7 碼**。
- 含小寫英文字者 55 筆；忽略大小寫後重複的工號 0 組。
- 對 ⑦ 的意義：目前能登入本系統的人（13 位）與可自動建帳號的人（資訊部 113 位）都是純數字；非數字工號只會出現在 DBA 預建的資格外人員。英數白名單擋得到底線、連字號帳號式工號（若日後 DBA 預建這類人員，他們會登不進來）。
