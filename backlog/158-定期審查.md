## 需求（SA §5.10，第 535～582 行）

- **審查對象**：已核准（APPROVED）且符合審查條件的帳號。審查條件（任一）＝資產分類 `IS_REVIEW_TRIGGER`＝1（目前 H01、H05、S01，不寫死代碼）、類別為門禁卡（DOOR）、特權（IS_PRIV＝1）。與第一階段 `ReviewRule.matches` 同一口徑。
- **審查期間帳號照常可用**：只標示審查狀態並通知審查人，不停用實際帳號。
- **審查狀態即時計算、不存欄位**，與帳號狀態是兩個獨立概念：正常／待複審（距下次應審查日 30 天內含當天）／逾期未審（已超過下次應審查日，或上次審查日為空）／審查異常（被駁回且尚未解除）。
- **雙簽**：Infra 主管半（REVIEW_SIGN_INFRA）與資訊治理主管半（REVIEW_SIGN_GOV）各簽一半、順序不限，兩半都通過才完成；完成時更新主表上次／下次審查日。每輪一筆簽核紀錄。
- **駁回**：任一半駁回＋原因 → 帳號標審查異常旗標（來源 REVIEW）、寄信給原申請人與資訊治理（GOV）；提供「直接發起停用申請」捷徑。異常只在修改／停用／重新啟用申請關卡 7 複驗通過時清除（決策 D42，第一階段已做）。
- **通知**：進入待複審時寄一次給審查人（每日排程 J04、每輪只寄一次）；逾期未審併入每週一彙總信 J02；駁回信。
- **其他接點**：待辦清單列出兩半簽核；首頁兩張卡（逾期未定期審查、審查異常待處理）；鈴鐺類別 2（審查異常尚未處理）；帳號刪除時取消進行中的那一輪；關卡 2～5、7 明細的審查異常警示（第 46 項 S10 已做，不分來源）。

量級查詢（唯讀）：
```sql
SELECT CASE WHEN A.IS_REVIEW_FLAG = 1 THEN 'ABNORMAL'
            WHEN A.LAST_REVIEW_DATE IS NULL OR A.NEXT_REVIEW_DATE IS NULL
                 OR A.NEXT_REVIEW_DATE < TRUNC(SYSDATE) THEN 'OVERDUE'
            WHEN A.NEXT_REVIEW_DATE <= TRUNC(SYSDATE) + 30 THEN 'DUE'
            ELSE 'NORMAL' END AS REVIEW_STATE,
       COUNT(*) AS CNT,
       SUM(CASE WHEN A.LAST_REVIEW_DATE IS NULL THEN 1 ELSE 0 END) AS NO_DATE_CNT
  FROM IM_ACCT A
  LEFT JOIN IM_ASSET_CLASS AC ON AC.ASSET_CLASS_ID = A.ASSET_CLASS_ID AND AC.STATUS = 1
 WHERE A.ACCT_STATE_CODE = 'APPROVED'
   AND (AC.IS_REVIEW_TRIGGER = 1 OR A.CATG_ID = 'DOOR' OR A.IS_PRIV = 1)
 GROUP BY CASE WHEN A.IS_REVIEW_FLAG = 1 THEN 'ABNORMAL'
               WHEN A.LAST_REVIEW_DATE IS NULL OR A.NEXT_REVIEW_DATE IS NULL
                    OR A.NEXT_REVIEW_DATE < TRUNC(SYSDATE) THEN 'OVERDUE'
               WHEN A.NEXT_REVIEW_DATE <= TRUNC(SYSDATE) + 30 THEN 'DUE'
               ELSE 'NORMAL' END;
```

## 設計

### 審查狀態（共用 SQL 片段，放 `ReviewDao`；清單、首頁卡、J02、J04、鈴鐺共用，不建 DB 檢視——「今天」照慣例綁參數 `:today`）

審查範圍（必須與 `ReviewRule.matches` 同口徑，補對齊測試）：
```sql
-- LEFT JOIN IM_ASSET_CLASS AC ON AC.ASSET_CLASS_ID = A.ASSET_CLASS_ID AND AC.STATUS = 1
A.ACCT_STATE_CODE = 'APPROVED'
AND (AC.IS_REVIEW_TRIGGER = 1 OR A.CATG_ID = 'DOOR' OR A.IS_PRIV = 1)
```
`AND AC.STATUS = 1` 一定要加：Java 端只取 STATUS＝1 的分類（`CodeDao`），`AcctDao.SELECT_BASE` 的 JOIN 不過濾；漏掉會讓用到停用分類的帳號 Java 與 SQL 判斷相反（第 139 項口徑）。

判斷順序（⑨A、⑥A、⑩A）：
```sql
CASE
  WHEN A.IS_REVIEW_FLAG = 1 AND A.ACCT_STATE_CODE <> 'DELETED' THEN 'ABNORMAL'   -- 審查異常（不分來源）
  WHEN (審查範圍) THEN                                                             -- 在範圍內才往下算
       CASE WHEN A.LAST_REVIEW_DATE IS NULL OR A.NEXT_REVIEW_DATE IS NULL
                 OR A.NEXT_REVIEW_DATE < :today THEN 'OVERDUE'                     -- 逾期未審
            WHEN A.NEXT_REVIEW_DATE <= :today + 30 THEN 'DUE'                      -- 待複審（含當天）
            ELSE 'NORMAL' END                                                      -- 正常
END                                                                                -- 其餘（不在範圍）＝NULL 不適用
```
**範圍一定要寫成正向 WHEN、不得寫 `WHEN NOT (審查範圍) THEN NULL`**（R2 實作時改掉的 bug）：帳號的資產分類查無或已停用時 `AC.IS_REVIEW_TRIGGER = 1` 是 UNKNOWN，`NOT (UNKNOWN)` 仍是 UNKNOWN，那支 WHEN 不成立就會落到逾期那支，把不在範圍的帳號算成逾期未審。R3 以後首頁卡、J02、J04、鈴鐺、簽核交易內重讀一律直接引用 `ReviewDao.REVIEW_STATE_EXPR`，不要另抄一份。
- 不另判「本輪已完成雙簽」：完成時主表日期往後推，自然回到正常。
- 狀態只用 SQL 算、不寫 Java 版；簽核 API 在交易內重讀狀態。
- 已刪除帳號要排除（刪除申請不清旗標，否則永遠算在異常裡）。
- 簽核條件（②A、⑨A）：狀態為 DUE 或 OVERDUE 才能簽或駁回；ABNORMAL、NORMAL、不適用都回 409。
